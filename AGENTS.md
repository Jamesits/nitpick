## Git
- On working alone (no parallel work), DO directly commit to master, DO NOT create new branches
- On parallel work, use worktree; DO remove the worktree after work done and merged back

## Coordination
- Coordinator should prepare shared resources and databases used by multiple workers; instruct the workers to use (if concurrency-safe) or copy them
- Coordinator must check disk space remaining after each worker returns; remove build cache and stale artifacts if needed
- Coordinator manages the concurrency. If a worker received a wrong split or need to further split the job: survey the work surface, plan the job split, return to the coordinator and stop; coordinator should schedule workers based on the new split.
- Each worker must only claim a single directory under the scratch directory; after work done, remove the directory
- If temporary artifacts are needed across different work items (e.g. databases, extracted files), worker might create a persistent directory under the scratch directory; when submitting results back to the coordinator, state the intention to persist it; coordinator is responsible for organizing these files
- DO NOT reference files under persistent scratch directories in git tracked files

## Documentation
- Use ASD-STE100
- DO use only short, simple and precise wording
- DO NOT correct yourself in the doc; ALWAYS remove the wrong statements and replace with correct ones
- DO state which claims are unverified or in question in the doc
- DO highlight deviations from typical algorithms/implementations or common sense
- DO NOT reference temporary items or artifacts outside the git repo (e.g. anything under `tmp`); directly include description, algorithms, methods or code/pseudo-code snippets
- DO NOT duplicate information; write in one place, and reference it from others
- Markdown rules: Use mermaid for graphs; use MathJax (inline or block) for formulae; escape absolute/determinant/pipe operators in tables; no ToC
- Plan stages and numbering is ephemeral, do not reference them outside a plan; summary the text instead

### Design (`doc/design`)
Write:
- Overview: the scope, the architecture, the interface/boundary (how it is connected to other modules)
- Technical decisions (Architectural only; reasoning of a specific implementation goes to code comments): considered and selected options each with a short reasoning; counter-intuitive decisions
- Usage (IFF different from the standard scaffold usage OR require manual timing): requirements/dependencies, pre/post run scripts, commands
- Testing: correctness/performance target and test method
- Future features/enhancements not in the current plan

Validate:
- Future enhancements and current plan do not interfere; otherwise STOP and ask

### Plans (`doc/plan`)
Numbered H3 sections, in dependency order, that consists of:
- Open questions about design docs and implementation
- TODO actions (what to implement/what problem to fix + how to verify if it is done)

Requirements:
- DO remove what you have done or validated
- DO NOT renumber the items when removing done ones
- DO NOT restate project-wide requirements

### Code Comment
- DO NOT restate what the adjacent code does; no step narration; DO document counter-intuitive things
- DO NOT reference the docs or the plan (stage names, etc.) within code or comment; the docs should reference the comment instead

### Git Commit Message
- Use Conventional Commits
- DO NOT reference the plan by id and stage names, write the summary directly

## Code
- Write modular code
- Write idiomatic, deterministic and reproducible algorithm implementation
- Fail early and soundly
- State machines should be explicit
- DO NOT test shim/passthrough code or external library behavior, unless the behavior is known to be wrong and we want to pin it, or we rely on undocumented/undefined behavior (in such case, state so in the comments)
- DO NOT test external data immutability (hashing/pinning)
- DO NOT test doc or comment format
- DO NOT parse doc or use doc as config files, UNLESS for automatically updating the doc itself
- If a test requires data generated by an external program: put the generated data in the repo and ignore it with `.gitignore`, and provide a re-generate script; the result should be reproducible or the code reading the data should explicitly accept the deviations; DO NOT put the generated data outside the repo
- DO NOT put pure descriptive strings without programmatic usage in data structures or machine readable part of the config, they belong to the comment
- When adding external dependencies, DO check and use the latest version where feasible

### Rust
- DO run clippy and cargo format after each job and fix all lint issues
- DO use nextest (`cargo nextest run && cargo test --doc`)
- DO search for existing libraries before creating one

### Tests
- DO write unit tests in a separate `<file>_tests.rs` file
